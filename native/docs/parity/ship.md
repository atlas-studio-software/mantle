Baseline: origin/master 6ca499f (2026-11-06). Inventory by lane native-plan-inv-ship.
Rows: 189 (UPD 58, INST 32, BOOT 14, PKG 36, DATA 49)   Scope: lib/updater.js, lib/update-watch.js, lib/features/updates.js, lib/packaged.js, lib/packaged-entry.js, lib/quartz-exe.js (launch path only), installer/**, .github/workflows/**, tools/install-autostart.ps1, tools/mantle-logon-task.xml, tools/mantle-elevated-setup.ps1, tools/restore-windows.cmd (as the installer uses it), README.md (Download, Install, Updating, Getting Windows back, Releases, Code signing policy, Privacy), PERF.md and tools/perf-budget.js, plus the data map in `native/docs/data-files.md` (every DATA row points at a data-files.md ID).

Prefixes: `UPD-` update check, banner, apply, watcher, release flow. `INST-` Mantle-Setup.exe, CI install test, SignPath, put-windows-back. `BOOT-` start at sign-in, logon task, elevated helper task. `DATA-` one row per persisted file, registry value or Chromium store the user would lose if the native app ignored it. `PKG-` packaged vs clone/dev, first-start warning, command-line entry, README claims that bind the code (privacy, signing), perf budgets.

The native app ships ONLY as an installed copy, so rows marked "clone-only" describe the git-clone updater. They are listed so the port makes a decision on each (drop, or keep for a developer mode), not so they are silently lost.

## Notes for the port
- The native app ships as an installed copy only. Everything under "Clone-only" (git, npm, sidecar bin-next swap, Try again / Skip, `update-watch.js`) can be dropped unless a developer mode is wanted; the watcher is never used by an installed copy because `apply()` refuses there. What matters natively: the 6 h check, the semver compare, the Download / Open release page / Later banner, the tray row, health reporting, and "run the new installer".
- Updates are installer-driven: Mantle-Setup.exe asks the running Mantle to quit via `Mantle.exe --quit` and verifies Windows is back (`verified` from restore-windows.ps1) before replacing any file. The native exe must therefore keep a working `--quit` that reaches a running instance, a stable name `Mantle.exe`, and a process-per-folder rule `put-windows-back.ps1` can see (it matches by exe path under the install dir and ignores `--type=` children, which are Electron-specific; a native process tree must satisfy the same "everything exits" check).
- `restore-windows.ps1`, `restore-banners.ps1`, `ramreclaim-undo.ps1`, `restore-osd.ps1` and `restore-windows.cmd` are NOT Electron code and must keep shipping at `<install>\resources\app\tools\` (paths hard-coded in installer.nsh, put-windows-back.ps1 and the Start menu shortcut) unless all three are changed together. The installer's `mantleBack` is the single most safety-critical piece: if Windows is not confirmed back it must change nothing.
- The updater compares tag vs `app.getVersion()`; the native build needs a version source equal to the tag (CI test asserts the installed package.json version equals the repo's). Keep semver with prerelease ordering.
- Installer stays unsigned until SignPath approves; the sign job is already wired and optional. If the native build changes the installer technology (MSIX, WiX, NSIS without electron-builder) the SignPath artifact name `Mantle-Setup.exe`, the draft-release asset name and the updater's asset name must stay identical or the updater shows "has no Mantle-Setup.exe yet".
- A Windows MSIX/Store route would change several promises here (no Authenticode SmartScreen text, different uninstall flow, `%LOCALAPPDATA%\Packages` data redirection). If the native app is packaged MSIX, `%APPDATA%\mantle` data would be virtualised: this is the biggest hidden trap for DATA carry-over, so prefer an unpackaged/NSIS-style install.
- Start at sign-in is a Task Scheduler task with a 15 s logon delay, `PT0S` time limit and a name that two scripts and the CI test look up (`Mantle`). Installing a new native exe over an old install must re-point the existing task (BOOT-005, DATA-037) and the uninstaller removes it only when it starts THIS copy.
- The first-start warning is a plain message box with a checkbox, shown before any shell change; the CI test drives it with UI Automation by control names ("Start Mantle", "Not now", "Also start Mantle when I sign in"). Keep those names (or update the test in the same change).
- userData: `%APPDATA%\mantle` (dev/packaged are the same folder on NTFS) and `%TEMP%\mantle-test-<name>` in test mode. The native app must read the SAME folder so every JSON under it carries over (data-files.md "Carry-over plan inputs"). WinUI 3 packaged apps with a package identity get a redirected AppData: use an unpackaged app or `ApplicationData` outside the package path.
- Electron-internal data a native app cannot read: Local Storage leveldb (desktop widgets switch, all Task Manager layout/choices), IndexedDB, cookies, and safeStorage ciphertext (`gcal\token.bin`, `client.bin`; needs `Local State` + DPAPI + AES-GCM). Plan: add an Electron-side export step that writes `<userData>\export\localstorage.json` (and optionally a DPAPI re-protected gcal token) BEFORE the switch-over; otherwise those few settings reset and the user signs in to Google again.
- App identity: AppUserModelID `com.owensilva.mantle` must carry over or notification-banner settings, jump lists and taskbar grouping reset.
- Registry hand-offs that point at the Electron exe and must be rewritten once: the `\Mantle` logon task, player ProgIDs (`MantlePlayer.Video/Audio`), `supervisor-main.json`.
- Update banners are Mantle's own island-glass toasts (lib/own-banners.js drawn by toasts.js), not Windows toasts: a native port needs the same banner component with sticky, tone (info/ok/error), detail text block, progress, and per-banner action buttons that can keep or close the banner.
- Perf budgets above are the contract for the native surfaces too (warm 50/100 ms, cold p95 400 ms, never 1 s; 0 idle CPU hidden; one R7 log line per open); the native port should keep the same log line so tools/perf-budget.js can judge it, or port the gate.
- Release flow is draft-only by design: a person publishes; CI never tags. The updater trusts only `releases/latest`.
- Windows PowerShell 5.1 only in installer scripts (no `?:`, no `&&`) because they run on machines with nothing else; keep it that way.
- Hard natively / WebView2 candidates: none in this lane. The nearest is the NSIS custom pages and message boxes (`MessageBox MB_RETRYCANCEL`), which a different installer framework must reproduce, and UI-Automation-driven CI that finds controls by caption.
- Row counts: UPD 58, INST 32, BOOT 14, PKG 36 (PKG-001..014 packaged mode, PKG-020..029 README claims, PKG-040..051 perf), DATA 49; total 189.

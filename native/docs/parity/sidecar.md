# Parity: The C# sidecar as a platform (SC-)
Baseline: origin/master 6ca499f (2026-11-06). Inventory by lane native-plan-inv-sidecar.
Rows: 119   Scope: sidecar/** platform behaviours only (protocol, lanes, deadlines, hang handling, exit/restore, hooks and hook health, taskbar guard, supervisor, elevation, recorder child, build), plus lib/sidecar.js, lib/supervisor.js, lib/hook-health.js for the contract. Per-surface verbs (a clipboard, Task Manager, Settings page, etc.) belong to the surface lanes; the file-by-file map is native/docs/sidecar-map.md.

In the native app the "wire" becomes in-process calls, so "Native: todo" on a protocol row means the behaviour (not the JSON) must be reproduced and tested at the new seam. Where a row says "process", the behaviour only has meaning if a separate process is kept.

## Notes for the port
- The whole sidecar is ~399 commands and 57 event names; the per-surface lanes own each verb's behaviour. This file only covers the platform. Pair each surface's parity rows with the sidecar-map.md row for its `.cs` file (the "Reuse" column says whether the file links as-is).
- 15 files are WinRT (list in sidecar-map.md 1.1). They compile today through hand-picked split winmds and a `Completed`-callback await (`WinRt.Await`), never `AsTask()`. Under modern .NET the same APIs come from CsWinRT (`TargetFramework net8.0-windows10.0.x`), which changes the await pattern and removes the three-route build; SC-172/173 are replaced, but each WinRT feature keeps its stated fallback behaviour.
- The 54 built-in verbs hide behaviours in the `Program.Run` switch (not in feature files); anything ported "per file" will miss them. Section 3 of sidecar-map.md lists verb to file.
- The ui lane is the WinForms message loop that owns the WinEvent hooks and WinForms timers. A WinUI 3 host needs a dedicated message-loop thread for them (SC-129), plus the dedicated hook threads (SC-120, SC-127, SC-128, SC-130).
- Coalescing, ttl expiry and the 1024 queue ceiling exist because of a live failure (2026-09-22: 32 timeouts and 49 late answers in 150 log lines while the bar's buttons did nothing). If the seam becomes in-process calls these protections still matter wherever a call can wait on a slow lane.
- The restore model assumes the shell-changing code can die alone. The taskbar region, notification-banner registry values, cursor clip and the per-window animation flag outlive a crashed host. Keep the taskbar guard, supervisor and restore scripts as separate processes (SC-082, SC-100, SC-074).
- Hardcoded identity: `Mantle.Sidecar` (EdgeClip, TaskbarHide.OtherHolder, Supervisor, TaskMgr, GameMode, AppPower) and `Program.OwnPid/ParentPid` (the "Mantle's own windows" gate SC-018) must be reworked for a single native process.
- `Lanes` priorities and apartments (SC-031) were measured; reproduce them rather than using the thread pool.
- Hook health (SC-124..126) depends on the main process telling the hook thread about wake/unlock; keep that call path.
- `lib/sidecar.js` `protocolAge()` refusal of shell changes on an exe without `dpiAware` is a build-skew guard; it disappears once host and sidecar code ship as one binary, but the guard idea (never touch the shell on a mismatched helper) applies to the supervisor/guard helpers.
- The Settings elevation broker re-launches this same exe with `--elevated`; the Task Manager helper is already a second exe. A native app needs one CLI mode or helper exe for each of: `--elevated`, `--taskbar-guard`, `--supervise`, `--record`.
